# Hush — instructions for agents

Hush is a native, portable Windows cleaning and tweaking tool (.NET 10, WPF). Read docs/DESIGN.md for the visual system and docs/HANDOFF.md for the current state before editing.

**The user's latest directions always win over anything written here or in Docs.** When a request conflicts with a rule in this file, follow the request and update this file so the rule stops blocking future work.

**Ask, don't assume (owner, November 13, 2026, binding):** when a request leaves a real choice open (how something looks or is laid out, what it shows, when it updates, what it does in an edge case, anything the owner would see or feel), **ask the owner how they want it before building, with the options in `AskUserQuestion`; never decide it on your own consent.** Obvious defaults already set by these rules do not need asking; open design and behavior choices do. Ask once, up front, with all the open questions together, then build exactly what was chosen. If the owner has said not to ask about something, follow that.

## Binding rules: read docs/RULES.md before any UI, animation, scrolling, performance or engine work

**Hush must feel smooth on an Intel i3 with 8 GB of RAM and integrated graphics; the developer's PC is far stronger, so "smooth here" proves nothing.** `docs/RULES.md` is the full rulebook (performance budgets, animation, smooth scrolling, UI, code, definition of done). The short version, most of it enforced by `tests/Hush.Tests/PerformanceRuleChecks.cs`:

- No window-wide effect (popup blur is OFF, `MainWindow.BackdropBlurEnabled`; popups use the dark scrim), no `BitmapCache`/`CacheMode`, a `DropShadowEffect` only where it is visible and only in the shared places, no endless animation outside the two scan cues, no new timer or polling, no blocking call on the UI thread, `AllowsTransparency` only on the app windows and the two popups; the main window uses the Glass look on Windows 11 by default (per-pixel transparency from the compositor: a layered window costs a full-window copy per frame), `--layered` goes back (`UI/WindowGlass.cs`).
- Build lazily: no popup/effect/list per row (`HelpMark` builds its popup when first shown), a card's data is read when the card is opened, nothing at page open may start `sc.exe`, WMI, a process list or a registry walk.
- Scrolling is `UI/SmoothScroll.cs` only (time-constant smoothing driven by `CompositionTarget.Rendering` only while a glide runs); never write per-screen wheel code.
- UI: shared styles only; a switch works like O&O ShutUp10++ (ON = this will be / is turned off or protected, OFF = left as it is; on Services and Scheduled tasks ON stages "turn it off" and the row says what will happen); every action button in Settings uses `AccentOutlineButton` so all share the Actions/Clean hover glow; a card opens with everything inside it closed; everything is ordered; explanations live in `HelpMark`/tooltips; a result text is never replaced at once; every state is designed; both themes, 800/920 wide, 75–120% size.
- **60 fps native, LOCKED (owner, November 9, 2026):** every animation runs at the display's own refresh rate. No `Timeline.DesiredFrameRate`, no frame-rate cap, no "low-resource" slowing of animation, ever *(test)*; moving content is pre-built shapes moved by transforms/opacity, with no opacity mask, clip or effect on it or on any ancestor *(test)*. The owner's words: "the app should feel 60fps native always". Measure with `scripts/Perf.ps1` (the cleaning cue is a budget line).
- **LOCKED ARCHIVES (owner instruction):** everything in `docs/locked/*` (today `mica-look`, the parked Windows 11 Mica look) is off limits: do not use, edit, move, delete, "tidy" or re-enable it unless the owner says so in plain words. `LockedArchiveChecks` fails if a file there changes. After an unlock, `pwsh scripts/Lock-Archive.ps1 <folder>` rewrites the checksums.
- **Definition of done for UI work:** `pwsh scripts/Verify.ps1`, render the previews (`HUSH_PREVIEW_DIRECTORY`) and LOOK at them in both themes, run `pwsh scripts/Perf.ps1` (budgets in RULES.md), `scripts/Build.ps1`, update HANDOFF/CHANGELOG with what was NOT verified. Never claim smoothness you did not measure.

## Product direction

- Hush is meant to grow into a broad, capable cleaner. New cleanup categories, deeper cleaning, Windows tweaks, startup/app management and other tools are welcome when the user asks for them. Do not refuse or water down a requested feature because earlier rules were stricter.
- Features may write to the system: delete files, change registry values, change Windows settings, manage services/tasks/apps, request administrator rights when a feature needs them. **Hush uses no Windows cleanup tool (no Disk Cleanup, no DISM) since 0.9 (user direction: they often removed nothing); it deletes what it cleans itself.**
- Default selections, age thresholds, which categories exist and how aggressive each one is are product decisions made per feature with the user, not fixed rules.
- **Next release is 0.9; its plan is docs/PLAN-0.9.md** (user decisions of November 9, 2026 are recorded there). Rules below marked *(0.9)* describe what the user wants now, even where the code has not caught up yet; build toward them, never back toward the old behavior.

## Simple mode and Pro mode (owner, November 11, 2026)

- **Simple mode is the default for everyone, old and new users** (`Preferences.ProMode` = false; an existing settings file has no value, so it starts Simple too). A **"Simple | Pro" switch in the header, left of the Settings icon** (`SimpleModeButton` and `ProModeButton`; the chosen word is lit and a line under it springs to the other word, `ModeUnderline`, transforms only; `UI/MainWindow.ProMode.cs`) switches. **Turning Pro ON asks first** (shared consent popup, "Switch to Pro mode?", a plain warm warning, action "Switch to Pro mode" left, "Stay in Simple mode" right); turning it OFF asks nothing. While ON (owner, November 12, 2026) the word "Pro" itself lights up in the accent color with a soft glow around the letters (a `LetterGlow` behind it: a tight glow around each letter, drawn once as a picture in code, no effect, shown by `ApplyProMode` only while Pro is on), with NO border and NO fill: a deliberate exception to the other highlighted buttons, which keep the `AccentOutlineButton` look (style `ProModeButton`, state in `Tag`). The Hush wordmark takes the same glow (`WordmarkGlow`), so the whole header says Pro is on; both effects go away in Simple mode. The spoken name is "Pro mode, on/off".
- **Simple mode:** an ordinary scan is **Safe items only** (`MainWindow.DefaultScanOptions`: the Quick Boost filter `SmartBoostController.IsSafeTarget`, so no registry, Recycle Bin or system tool), Take a look opens the Safe list directly (one group: no chevron, plain "Select all", Back leaves Review), and **Settings shows only the Info card (CPU/memory/drive/temporary-files bars and Boost), Appearance (size and main color) and the red "Windows Update is off" line**; Process, Administrator, Smart Boost, Browser data, Services, Scheduled tasks, Privacy, More impact, Windows Update and the footer are hidden (not even read: Settings skips the Windows choices, startup apps and process list in Simple mode). **Pro mode is the app exactly as before.**
- Switching mode never deletes or undoes anything: it clears the Review results (a Safe-only scan and a full scan differ; scan again), and anything already on (Automatic Boost, tray, start with Windows, services, tasks) keeps running while hidden. Explicit scans (Quick Boost, Boost, Browser data) keep their own options. New Settings cards and Review features are Pro-only unless the owner says otherwise. Test seam: `MainWindow.TestProMode` (the test runner starts every window in Pro mode; `ProModeChecks.cs` checks the product's own default and the switch).

## Administrator mode (0.9, user direction)

- Hush asks **once** (first run, right after the Terms; existing users once on their first 0.9 start): "Let Hush run as administrator?" The answer is `Preferences.RunAsAdmin`; Settings has a switch to change it. *(0.9, user request, same card)* The **Administrator card also holds two more switches: "Minimize to tray"** (`Preferences.MinimizeToTray`: minimizing hides Hush in the notification area, `UI/TrayIcon.cs` = plain `Shell_NotifyIcon` with a message-only window, no timer; left click opens, right click Open/Quit; turning it off while hidden restores the window; the close button still quits) **and "Start with Windows"** (`Preferences.StartWithWindows`: Hush's own value in HKCU Run, `Admin/StartupRegistration.cs`, command `"exe" --startup`; it opens quietly, minimized or in the tray; re-pointed to the running copy at each start; with administrator mode the elevated copy learns it from a one-minute note `startup-hint.txt` because the task cannot carry arguments; a start with `--startup` never wakes an already running Hush; uninstall removes the entry; a portable copy in admin mode asks Windows' prompt at every sign-in). Tests use fakes (`ITrayIcon`, `IStartupRegistration`, `MainWindow.TrayFactory/StartupRegistration`): never a real icon or Run key. If the user agrees, Hush **always runs elevated** from then on, so system Temp, Prefetch, trace logs, Windows Update files and the removal of Windows.old work without extra prompts.
- Installed copy: agreeing moves it to `C:\Program Files\Hush` and registers one "run with highest privileges" scheduled task (`Hush (administrator)`) that the shortcuts start, so there is no UAC prompt per start. The task must only ever point at an exe in an admin-only folder (never `%LOCALAPPDATA%` or a portable folder: that would let other programs get admin silently). Portable copy: relaunch with Windows' own UAC prompt each start. Turning the switch off removes the task and restores normal shortcuts.
- **Elevated work never trusts files other programs can write (0.9 audit):** an elevated Hush stages the update (the downloaded app, its recorded hash, `install.json`, the helper copy), the uninstall helper and the Task Scheduler XML only under `%ProgramData%\Hush` (`Admin/AdminOnlyDirectory.cs`): created with an ACL for SYSTEM and Administrators only, and checked again before every use (owner, and no allow-rule that lets anyone else write, delete or change permissions); a folder that fails the check is refused, never repaired and used. A normal (not elevated) Hush keeps staging in `%LOCALAPPDATA%\Hush`. Histories that an elevated Undo reads (services, Windows Update switch, Windows settings) are checked against an allow-list (catalog names, fixed lists, leftovers whose file is still missing), never only a deny-list. Tests: `StagingTrustChecks.cs`, `ServiceChecks.cs`.
- **Update receipt, close and crash note (0.9 audit):** a start that only hands over to an elevated copy writes the update receipt first (`App.ReceiptBeforeHandOver`), or the updater would roll the update back. Closing during a scan/clean waits at most `MainWindow.CloseGraceMilliseconds` (a Windows change: 30 s), then closes; never wait without a limit. Unhandled errors go to `Logs\crash.log` (`CrashLog`, local only). Boost (button or automatic) and a scan/clean never run at the same time (`BoostWorking`). Cleanup roots are long-form paths (`CleanupEngine.LongPath`); Windows.old measuring is time-boxed and cached.
- **Temporary files (user decision, kept after the audit):** user %TEMP%, Windows\Temp and the app temp folders are found at any age and deleted completely when the person chooses, including through Boost. Do not add an age floor; the root guard only refuses hostile roots.
- If the elevated account is not the signed-in user, user-profile locations are cleaned only as the signed-in user, never in the admin's profile by mistake.
- Being administrator changes only what is reachable: scan stays read-only, every delete re-verifies and logs, confirmations, the Never-touch list and the Defender/restore-point rules are unchanged. Tests use fakes for the task scheduler and elevation; never register a real task or move the real app on this PC.
- **One Hush at a time (0.9):** a per-user mutex; a second start brings the running window to the front and exits (also across elevation levels). Setup/uninstall have their own.

## Safety basics (keep these)

These are the minimum protections; they exist to keep users' data safe, not to limit features.

- Show the user what will happen before any destructive or system-changing action, and require a confirmation click. Scanning/previewing must not change anything.
- **The Clean confirmation (owner, November 11, 2026):** **Simple mode** shows only the amount as the title ("Clean 5.1 MB?"), ONE calm line ("Only safe temporary files. Your own files are never touched.") and "Clean" (left) / "Not now" (right): no breakdown, no list of what happens, no home note. **Pro mode** keeps the breakdown (a raised block with a colored line, name and amount per risk group and per category, on shared columns so names start at one x and amounts end at one right edge in monospace figures), a short list of what will happen (permanent deletion, per-category consequences, "Security data and restore points are never touched.") and "Clean selected" / "Keep my files"; the Advanced consent box stays. **After a clean the person stays on Home** (no automatic jump to the Review page) with the finished-mission gauge: the "100%" takes the accent color and a soft glow (the `GaugeValueGlowEffect` resource, attached to `GaugeValue` only while that finished state shows and removed by `ResetGauge`), and the ring glow is stronger than after a scan (`CompleteGauge(mission: true)`).
- Log what was deleted or changed (local logs in `%LOCALAPPDATA%\Hush`). Back up registry keys before deleting or changing them, and offer Undo for Windows setting changes where Windows makes it possible.
- Never delete the user's personal files (Documents, Pictures, Desktop content, etc.) unless the user explicitly picks them in a feature built for that.
- After a clean, the status line keeps its result as ONE short line ("Cleanup complete · X freed", owner: "sleek and minimal", November 11, 2026) with a second line only when files were left alone; the details (cleaned, skipped and why, disk-reported, still found) are on hover; or "Cleanup couldn't finish."; nothing may replace it at once (a test covers it).
- Be honest in the UI: no fake "speed boost" or performance claims, no claiming success that wasn't verified.
- Never store, log or embed credentials or tokens.

## Cleaning architecture and permanent safety rules

All cleanup rules live in two places only: `CleanupEngine.DefaultTargets()` (locations, patterns, ages, protected flag, category) and `ReviewCategory.Definitions` (category id, title, risk level, description, section). Add a category or location there, nothing elsewhere.

- **Risk levels** (`SafetyLevel`, three colors): *Safe* (calm green, `SafetyPalette.Good`: #5CC98F Dark, #2E8B57 Light; also used for positive status such as "You're up to date" via `GoodBrush`) = verified disposable files: today only Temporary Files and Thumbnail Cache; only Safe items are selected by default. *Review* (orange) = browser caches, shader caches, developer caches, logs, dumps, traces, Windows Update/Delivery Optimization/setup files, broken shortcuts; always opt-in. *Advanced* (red) = irreversible, recovery-related or with real consequences (Previous Windows Installations, Recycle Bin, registry, browser cookies, and `AppDownloads` = Large App Downloads and Installed App Files: Unity Asset Store downloads, Fusion 360 `webdeploy`, CapCut `Apps`, Codex runtimes, Zed downloaded tools, GitHub Desktop update packages; added November 9, 2026 at the owner's request, each only while its app is closed); always opt-in and the confirmation keeps Clean disabled until the consent checkbox is ticked. Never raise a category's default selection without the user asking.
- **Catalog:** `ReviewCategory.Definitions` lists every category (with a `GroupId` for documentation: Recommended, Additional system items, Application cleaning, Computer usage traces). *(0.9)* The Review page first shows three color groups (Green Safe, Amber Review, Red Advanced) with size and counts; clicking one opens its categories in catalog order with the same card style, checkboxes and animations, and the shared Back button returns to the groups. *(0.9, user direction)* One bar sits above both views: on the **overview** "Select all categories" ticks Safe, Review and Advanced together (as it always did), and each group row has the group's colored line (the category-row line style, no dot) and its own checkbox in that color that selects or clears just that group (mixed when partly selected, `ReviewGroupSummary.SelectionState`, `GroupSelect_Click`, which marks the click handled so it never also opens the group: a `Click` bubbles from a nested checkbox to the row's button; only the rest of the row opens the group). Soft dividers (36 DIP in, opacity 0.45, the same hairline as between the category cards) sit under the Select-all bar on the overview (`OverviewDivider`) and between the groups (`ReviewGroupSummary.DividerAbove`; do not use `AlternationIndex` for this, it hid every divider); **inside a group** a chevron-only Back (`ChevronBackButton` style, `GroupBackButton`, no text) sits beside the checkbox, which reads "Select all in <group>" and covers only that group, and Expand all appears. Only the layout changed (the old `GroupId` section headers stay removed). Only groups and categories with detected items are shown. **Order and outlines (owner, November 11, 2026):** category cards go Safe, Review, Advanced and, inside each level, **largest first** (`SortDescriptions` on the category view: Safety, TotalBytes descending, `CatalogOrder`); the files inside a category are **grouped by app/location first (the one holding the most first; `Group`), then by folder, largest file first** (`ReviewCategory.OrderBySizeAndLocation`, one sort per scan result), and **a card holding more than one app gets a sub-heading row (name, count, size, a short line in the card's color) before each app's files** (`ReviewCategory.Rows`, `ReviewSubHeading`, `ReviewRowTemplateSelector`; built once per scan result). **The Advanced "Large App Downloads and Installed App Files" card was split into one short card per app** (`ReviewCategory.AppDownloadIds`: Unity Asset Store, Autodesk Fusion 360, CapCut, Codex, Zed, GitHub Desktop; the old `AppDownloads` id is gone). **The lists inside a card scroll with the wheel and have chevron steps** (`FileListBox`/`StepScroll`/`StepScrollBar`, `UI/ScrollSteps.cs`): an up and a down chevron at the ends of the list's scroll bar, each click moves the list exactly one item (holding repeats, glides like the wheel); the wheel over such a list scrolls the list first (the fix: `SmoothScroll.PixelScrolling` reads ScrollUnit from the list that owns the panel, because reading it from the panel always said "by item" and the page behind scrolled instead; `ReviewOrderChecks.RunListUi` reproduces it); a **fully selected group row on the overview gets an outline in its own color** (green Safe, amber Review, red Advanced; the `GroupOutline` overlay, like the `SelectionOutline` of a selected category card). Tests: `ReviewOrderChecks.cs`. "Other Browsers" (`BrowserOther`) is the last category in the catalog. After a scan, the Clean confirmation from Home says it cleans only the green (Safe) items.
- **Never remove automatically (even as Advanced): Defender protection history/quarantine, certificates, security logs, restore points, recovery data.** *(0.9, user direction, replaces the old "only through Microsoft's tools" rule)* **Previous Windows installations are removed by Hush itself** (`Cleaning/WindowsOldRemoval.cs`: only the folder `Windows.old` at the root of the system drive; administrator mode required; Hush takes ownership in-process of an entry only after Windows refused a plain delete; links are removed as links and never entered; it says exactly how much was removed and how much Windows still protects or uses; Advanced, never selected by default, consent checkbox; the old Users folder goes too and the confirmation says so). **The component store (WinSxS) and Defender protection data are NOT deleted directly and have no row**: raw WinSxS deletion breaks Windows servicing, and Defender protects its data itself (bypassing that is not Hush's job); the DISM component rows and the Disk Cleanup Thumbnails/Defender handler rows were removed (the direct Thumbnail Cache and Defender support-log categories remain). Browser passwords, bookmarks, saved sessions and form data are never in any rule; history is Review, cookies are Advanced and need the browser closed. Firefox `places.sqlite` (also holds bookmarks) is never listed.
- **Scan is read-only; every delete re-verifies.** Delete uses an exclusive handle and re-checks approved target, pattern, final path, link count, size/timestamps and age. Keep these checks when changing the engine. Directory chains are link-checked once per folder per clean; the per-file final-path comparison is what catches a swapped link.
- **No file-count limit.** The scan streams (one enumeration pass, no candidate list, no global path set); where targets overlap the most specific target owns the files (`PlanOverlaps`). A `CleanupItem` is about 256 bytes retained per file (shared folder string, side object for rare fields). `ScanOptions` can filter targets (Safe-only for Quick Boost), count without keeping items (monitoring), slow progress and lower thread priority (low-resource). Clean logs intent per batch of 64 before acting, throttles progress to ~50 ms, and records free disk space before and after (`CleanupResult.MeasuredFreed`).
- **Scan watchdog (a scan can never hang silently):** every location is scanned on its own worker (`ScanTarget`, results in a `TargetRun` merged only when the location finishes); the coordinator watches a heartbeat that the worker updates with every entry (also filtered-out ones) and every protected-file probe. A location silent for `ScanOptions.StallMilliseconds` (30 s) is abandoned, counted in `ScanResult.Stalled`, noted in `Logs\scan-issues.log` and shown in the scan note; an abandoned worker never touches shared state again. Stop returns within about 1.7 s even while a location is stuck. The registry, Recycle Bin and system-tool (Windows.old, clipboard) steps run guarded with a time limit too. Keep per-entry heartbeats and the merge-only-when-finished rule when changing the engine; tests use `ScanOptions.OnTargetStart` to block a location on purpose.
- **`DeletableOnly` targets** are system-protected locations: a file is listed only if this user can open it for deletion right now; permission errors there are not "skipped locations". Every location under the Windows folder (except Windows temp) must use it.
- **Patterns**: `Pattern` may list several wildcards separated by `;`. Only temp and cache targets may use no pattern. `ExcludeFolders` skips named sub-folders. INetCache is never cleaned as a whole (it holds Outlook/Word attachment copies and, on some PCs, whole app data folders): only its legacy `IE`, `Content.IE5` and `Low\Content.IE5` folders. The Windows folder itself may only be a target for the single file `MEMORY.DMP`.
- **Never touch (the first group is enforced by tests/Hush.Tests/CategoryChecks.cs):** personal folders (Documents, Pictures, Music, Videos, Downloads, user profile root), Program Files, System32/SysWOW64, `WinSxS`/the component store (and `Windows.old` as an ordinary cleanup target; it has its own dedicated removal), `Installer`/`$PatchCache$`, `Package Cache`, recovery/boot data, INetCache as a whole (see Patterns). Also never add: jump lists (`AutomaticDestinations` hold pinned items), Office `UnsavedFiles`/OfficeFileCache (unsaved or unsynced work), Spotify `Storage`/`Data` (may hold offline downloads), the pnpm store (hard-linked), Windows Defender data, WMI/driver stores, fonts/icon caches that Windows needs to rebuild, and registry MRU lists (Recent Documents History uses only Office recent-file shortcuts). Prefetch is a Review (opt-in) category since the user asked for it (`Prefetch`, `*.pf` only, deletable-only): it frees little and the next launch of each program can be a little slower, so it is never Safe. **Temporary Files age (0.9, user direction):** Hush finds Temp files of any age by default (user and Windows Temp); the Settings > Temporary files section and `Preferences.TempAge` are removed. Files in use are always skipped (exclusive-handle delete) and the delete-time re-check stays. App rules added from a real PC survey: CapCut `User Data\Cache`, Office add-in cache (`16.0\Wef`), and downloaded updater installers (`<app>-updater` / `*.update` folders: only `installer.exe`, `current.blockmap` and the `pending` folder).
- **Root guard (0.9 audit):** after the default targets are built, every location is checked (`CleanupEngine.IsAcceptableRoot`, `CurrentRootRules`): a drive root, a location inside a personal-data folder (Documents, Pictures, Music, Videos, Desktop, Downloads, OneDrive), or one that is or contains a personal/protected folder (profile, its parent, AppData, ProgramData, Program Files, System32, Windows) is dropped and noted in `Logs\scan-issues.log`. This matters because the temp location follows the TEMP/TMP variables, which can point anywhere. Single-pattern, non-recursive locations (Desktop `*.lnk`, Windows `MEMORY.DMP`) only need to be no drive root. Add new roots only where they pass this check.
- **Deep-clean scope:** user caches only inside the current user's AppData (enforced); system-wide categories (Update, Delivery, Setup, Windows Logs, Installer Leftovers, system dumps) must use `DeletableOnly`. Targets are added only when their folder exists, so a scan visits just what is installed. Usage Traces removes only recent-file shortcuts (`*.lnk`) from the Windows and Office `Recent` folders, never the files they point to.
- **App discovery (`AppDiscovery.cs`):** apps without a hand-written rule are found by what they are, inside the current user's AppData only, always Review (opt-in), never Safe. A Chromium data folder (Electron, WebView2, CEF: a `Code Cache` or `GPUCache` next to `Cache`) gets only its cache sub-folders listed (`Cache`, `Code Cache`, `GPUCache`, Dawn/shader caches, `blob_storage`, `Cached*`); never IndexedDB, Local Storage, Network (cookies), sessions, extensions or any profile data. Such a target carries `LockFiles` (Chromium's `lockfile` exists while the app runs): scan and clean skip it while one exists. Firefox-family browsers other than Firefox (Zen, Waterfox, LibreWolf...): `Local\<app>\Profiles\<profile>\cache2` and friends, with the app name as the process guard; Roaming profiles are never entered. Folders named `Logs`/`Log` (only `*.log`, `*.log.*`, `*.etl`, 14 days, category `AppLogs`), `Temp`/`tmp` (14 days, `AppTemp`), `Crashpad` (`reports`/`completed`/`pending`/`new`, only `*.dmp`/`*.meta`) and `CrashDumps` (`*.dmp`). Never entered: Microsoft, Programs, Temp, Hush (its own audit logs), the browsers, Windows' own Store packages, node_modules, Android\Sdk. A location a hand-written rule owns is not added twice. The walk is bounded (60,000 folders, 5 seconds) so it cannot slow the first scan. Tests: `tests/Hush.Tests/DiscoveryChecks.cs`; `Hush.Tests.exe --target-report` lists every location built on this PC (read-only).
- **Honesty:** cleaning frees disk space; do not claim it makes Windows or apps faster (caches and shader caches make the next launch slower until rebuilt). Never add "speed boost" wording.
- **Cleaning starts no Windows tool (0.9, user direction):** nothing in Hush launches Disk Cleanup, DISM or a cmd line for cleaning, so no console or Windows window can appear while cleaning (`SilentToolChecks` scans the source for cleanmgr / dism.exe / /sagerun). The Review rows that used to say "By Windows" are gone or direct (the unsized label is now "—").
- **System tools** (`ISystemTools`, `SystemTools.cs`): Previous Windows Installations, component cleanup and clipboard history are `CleanupKind.SystemTool` items. The engine re-probes before running and rejects unknown tool ids. Tests use a fake; never start a real tool, UAC prompt or clipboard clear to test.
- **Browser data is Settings-only:** browser history and cookies (`ReviewCategory.SettingsOnly`) are never part of a normal scan, Quick Boost or Automatic Boost (`CleanupEngine.Scan` leaves them out unless a scan is given an explicit `Include`). They are chosen in Settings > Browser data: history is marked Review (orange), cookies Advanced (the Clean red) and choosing cookies opens a warning popup; "Review and clean…" scans only what was chosen, selects it and shows the normal confirmation (with the Advanced consent box). Saved passwords, bookmarks and sessions are never in any rule.
- **Temporary files meter (Info card):** it counts the Safe temp files that are ready to clean. *(0.9)* With no age limit, the "too new" split (`JunkReading.HeldBytes/HeldFiles`, `ScanOptions.MinimumAgeOverride`) is removed from the tooltip and Boost popup.
- **Boost chip (owner, November 13, 2026):** ALWAYS shown beside the header wordmark (next to the update notice), in Simple and Pro mode, never hidden: a small `AccentOutlineButton` pill with a heartbeat line and "RAM 62% · CPU 14% · 1.4 GB" (0 MB when nothing to clean; a click still opens "Boost now?"); it runs the same Boost flow as the button below and shows its stages. RAM/CPU: a 5 s timer approved by the owner, only while the real window is in front and not minimized (`SmartBoost/MainWindow.BoostChip.cs`, own `ResourceMonitor`); the MB figure is one count-only read 3.5 s after start and after a clean/Boost. **Motion (owner):** a text change (Boost stage, new figures) slides up (300 ms, always finishes, never loops); while Boost runs the chip's OWN BORDER draws itself from the top centre clockwise until it closes (`UI/BorderSweep.cs`, mirrors the Boost bar via `UpdateActivity.Mirror`; stays closed a moment, then fades; never a line under the text).

The header logo must look the same whether the window is active or not (no brighter active state). Text controls ease their color (`TextButton`: Muted→Text; `AccentTextButton`: accent→`AccentHoverBrush`); glowing buttons gently intensify their existing glow; checkboxes ease a neutral hover ring; scrollbar thumbs ease opacity.
- **Checkbox** (App.xaml): checked border, tick and mixed dash share the same accent brush; unchecked stays neutral. All rings share one geometry with layout rounding off, so edges stay smooth.
- **Popup buttons (locked by a test):** in every popup (clean confirmation, Windows changes, consent/terms/Boost/update confirmation, About, Setup) the action (Clean selected, Boost, Update now, I understand, Install, Check for updates) is on the LEFT and the button that leaves (Keep my files, Not now, Cancel, Close, Quit, Run without installing) is on the RIGHT, and the action comes first in tab order. New popups follow the same order.
- **Back** is the shared `BackButton` style (`Content="Back"`, chevron + label centered, label right edge aligned to the page edge). Never hand-build a Back button.
- **Smooth scrolling (0.9, user request; `UI/SmoothScroll.cs`, installed by `App` for every `ScrollViewer`):** the mouse wheel and touchpad glide (an eased render-thread animation, 200-420 ms, retargeted by each further notch, distance = Windows' wheel-lines setting) instead of jumping. The innermost scroll area under the pointer that can still move takes the wheel and hands over at its end; the scrollbar, keyboard and code such as `ScrollToTop` cancel a glide at once; item-based (logical) scrolling is left to WPF, so a virtualizing list must set `VirtualizingPanel.ScrollUnit="Pixel"` (the Review file lists do); Ctrl/Shift/Alt wheel is untouched. New scroll areas get it for free; never write per-screen wheel code (`SmoothScrollChecks`).
- **Scrolling**: page-level scrollers use `PageScroll` (10 DIP overlay bar, 16 DIP end-of-scroll padding) so the last card is never clipped and content width never shifts. Gutters on both sides of a scrolled list are equal; the bar lives inside the right gutter. Cards in a scrolled page have 16 DIP gaps.
- **Scan-complete area (Home):** "Scan Completed" is plain upright status text (18) with no border; below it the found-files details, and below that two buttons of exactly the same size and font (140x40, 18): **Take a look** (`AccentOutlineButton`: the Clean button's shape and glow in the theme accent) and **Clean** (the Clean red), side by side 14 apart. Never an arrow and never a looping animation (the breathing glow was removed by request). The old underlined link, then the single accent button, were replaced at the user's request (0.8.3).
- **Typography (locked by `TypographyChecks`, which scans the XAML and the running window):** italic is used ONLY for the home heading "Make more room to breathe" (the Hush logo in the header, About and Setup is upright Medium 500 since 0.9); every other text is upright, including the scan-complete button. **Page titles** (Review files, Settings) use the one shared `PageTitle` style (29, Medium 500) at the same position; **popup titles** (confirmations, Windows changes, consent, Setup) use `PopupTitle` (28, Regular); **Settings card titles** use `CardTitle` (18, Medium, accent). Never hand-style a title (no `FontSize`/`FontWeight`/`FontStyle` on it); change the shared style instead. Small text sizes are the shared 15/16 resources in App.xaml, never per-screen literals.

## Build and test

- `scripts/Verify.ps1` runs the whole suite (including `--verify-smart-boost`; use `Hush.Tests.exe --stress-scan` separately) (add `-Configuration Release` if an open preview locks files). Keep it passing before handing work back.
- When a feature intentionally changes behavior, update or remove the tests that encoded the old behavior instead of bending the feature to satisfy them. Add tests for new deletion/system-change logic using fixtures.
- **Always leave a fresh exe (user direction, 0.9):** at the end of any turn that changed the app, after `Verify.ps1` passes, run `scripts/Build.ps1` so `artifacts\Hush-Portable.exe` (and `Hush-Setup.exe`) are the current source and the user can test live; say where it is. `Tidy.ps1 -Apply` removes bin/obj but never `artifacts\`, so rebuild after it too. Local only: building never means publishing.
- `scripts/Build.ps1` writes into one flat folder: `artifacts/Hush-Portable.exe` and `artifacts/Hush-Setup.exe` (the same program; started by that name it opens setup), their upload zips `Hush-Portable.zip` and `Hush-Setup.zip` (only zips are uploaded to GitHub) and `artifacts/WHICH FILE.txt`; it removes the old nested `artifacts/Hush/`. *(0.9, user-approved, done)* Releases are self-contained and compressed (the .NET runtime is inside the exe, ~60–70 MB) so users never need to install .NET; that is the Build.ps1 default (`-FrameworkDependent` makes the small build for local tests only) and the README/WHICH FILE.txt no longer mention the runtime. A clean-VM check is still the owner's. `scripts/Tidy.ps1` lists (and with `-Apply` removes) rebuildable `bin`/`obj`/fixture/preview clutter, skipping folders with a running program; it never touches `artifacts/`, `Backups/` or other projects.
- `scripts/Backup.ps1 -Label <name>` makes a source + portable snapshot in Backups/ (local only, not in Git). It re-reads every archived file and verifies its SHA-256; it needs `artifacts/Hush-Portable.zip`. If Hush-Portable.exe is running from `artifacts`, `scripts/Build.ps1` stops with a clear message instead of half-updating (never kill the user's app): publish to a temp folder and zip that instead. Take a verified backup before large engine/cleanup changes.
- `Hush.Tests.exe --benchmark` prints scan/clean timing and allocations on a synthetic fixture; `--scan-report` runs a read-only scan of this PC and prints what each category would offer (it never cleans). Use it after adding locations to check paths against the real machine (see tests/Hush.Tests/README.md).
- **UI work: look at it.** Tests render both themes to PNGs when `HUSH_PREVIEW_DIRECTORY` is set; open them (and zoom/measure glyph alignment) before and after UI changes instead of trusting numbers alone.
- The project folder itself is the Git repository (remote `ShepherdGal/Hush`, branch `main`). `.gitignore` keeps bin/obj/artifacts/Backups/settings/logs/binaries/secrets out; release binaries go to GitHub Releases, never into Git. Commit, push, tag and release only when the user asks.
